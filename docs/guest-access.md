# Guest email access

P15 consumes a delivered CREATE or MANAGE challenge and persists its grant in one transaction. Token hashes locate locked challenges; strict expiry, purpose and browser checks precede consumption. CREATE reuses the normalized stable identity and gives one 30-minute creation scope. It does not enroll an account. MANAGE gives only the named booking's scope for two hours; redemption rechecks that booking's current delivery address and retains its original owner identity. A changed delivery mailbox cannot transfer identity, history or quotas. ACCOUNT and CONTACT are separate workflows and cannot redeem through this component.

The grant ID and returned metadata are internal references, not bearer authorization. P17 must attach persisted state to the server-owned browser binding and recheck current grant expiry/revocation for access. Public redemption and management recovery endpoints await those protections. Request bodies must never choose the browser hash, and token/metadata string representations are redacted.

The internal management-recovery request accepts the exact public booking reference and normalized current delivery address. Matching and unknown requests return the same empty accepted result; no matching identifier or booking history is returned. A match queues the existing encrypted, single-use MANAGE proof and creates no grant, identity or account. Terminal bookings remain recoverable for status and financial follow-up. The reference alone is never authority. Storage failures remain safe failures; public CSRF, origin checks and distributed address/IP throttles must precede this workflow when P17 exposes it.

Lookup and encrypted delivery issuance use separate bounded transactions. If the delivery contact changes between them, the final locked redemption rejects the old-contact link. Recovery retains the booking's original customer identity even when its delivery mailbox differs. MANAGE links may be opened on a different browser; the resulting grant binds to the redeeming server-owned browser. CREATE and ACCOUNT messages retain the requesting-browser instruction.

P09 must consume CREATE while holding the scheduling resource lock in its booking transaction. Set that grant's booking and consumption time together, then derive one MANAGE grant for the same owner/browser/booking. The derived grant's issue time equals consumption and its expiry cannot exceed the original creation-grant issue time plus two hours. The original CREATE identity, scope and 30-minute expiry remain immutable for receipt/replay correlation. Database constraints enforce provenance, owner agreement and single derivation. Previously unbound grants are preserved as revoked during upgrade.

Challenge and grant creation commit together, so a failed grant insert rolls back both new identity creation and consumption. Independent callers serialize on the challenge; different valid proofs for one mailbox reuse one identity. Booking locks precede challenge locks for management to align with future contact-change commands. Authentication delivery remains outside this transaction; an email rendered concurrently with redemption can contain a now-inert link. The worker separately erases consumed challenge ciphertext.

The database suite uses synthetic identities, encrypted delivery preparation and a real PostgreSQL container. It covers replay, wrong purpose/browser, expiry, lock waits, changed contact, rollback, stable identity races, grant provenance and legacy revocation. It adds no HTTP endpoint or authentication bypass.
