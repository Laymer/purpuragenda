# Configuration mutation authority

Schedule/policy mutations capture database time once after the resource lock. They then lock and recheck the persisted enabled/enrolled administrator and browser-bound session, security epoch and revocation before reading an idempotent result or changing configuration. Idle and absolute deadlines remain strict; fresh MFA must be younger than ten minutes, with equality expired. Neither session issuance nor factor authentication may be later than the captured command time.

A different guarded request can legitimately resolve the same session and advance last_seen_at after resource time was captured but before the configuration command locks the session row. That mutable activity is accepted; treating it as a future authorization fact incorrectly rejects concurrent valid requests. The command does not recapture time. Its activity update uses GREATEST so it cannot move the session's activity backward. A revocation that commits during the same interval still denies the command without configuration/audit/idempotency effects.

The explicit nonfuture authenticated_at bound preserves the factor-time invariant independently of mutable activity. Read-only repeatable-read queries use a consistent snapshot and retain their own nonfuture activity checks. This correction changes no contract, route, migration, resource lock order or booking snapshot.

ConfigurationAuthorityPostgresTest uses normal password/TOTP HTTP login and real persisted session resolution/revocation to test the interleaving, one captured time, factor-time and fresh-MFA microsecond boundaries and twenty simultaneous session resolutions/idempotent configuration requests. Mandatory reporting requires both its nine actual cases and the existing fifteen configuration PostgreSQL cases, rejecting missing, incomplete, failed and skipped reports.
