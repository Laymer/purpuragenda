# Optional customer accounts

An account is optional and explicit. A guest proof (CREATE or MANAGE) never creates one. Enrollment needs a delivered ACCOUNT email proof bound to the requesting browser and a chosen password. In one transaction `PostgresAccountEnrollment` consumes the proof (strict expiry, single use), reuses or creates the verified stable customer identity for that mailbox, inserts the account and an empty profile and audits `ACCOUNT_ENROLLED`. It issues no session and no grant. Existing bookings, grants and quotas stay with the identity and are not transferred or merged; an identity with an account cannot be enrolled again, and the rejected proof is left unconsumed.

The login identity is the verified mailbox at enrollment and is immutable (a database trigger also requires it to equal the identity's email). Passwords use the administrator policy (15 to 128 Unicode code points, never trimmed or normalized) and Argon2id 64 MiB, 3 iterations, one lane. They are hashed before the transaction, buffers are cleared, and only the encoded hash is stored. A new hash requires a higher `credential_version`, so history cannot be rewritten or rolled back.

Failed account logins are reserved before any password work as `ACCOUNT_ATTEMPT` (five per fixed fifteen minutes per account and network), like administrator attempts. Real PostgreSQL tests cover replay, wrong browser and purpose, expiry equality at one microsecond, existing accounts, rollback and 20-way races across independent connections.

Migration015 is preserved;016 closes SQL CHECK's NULL/UNKNOWN loophole by explicitly requiring every enrolled credential component, while retaining all-NULL legacy fixture rows. The validated versioned constraint is checked through public PostgreSQL catalog metadata for readiness:015 remainsDOWN until016 is applied. The additive upgrade preserves existing account IDs, hashes and timestamps and reruns idempotently. Proof time is captured once after acquiring the challenge lock; a proof expiring while that lock is held is rejected when the wait ends.

Account authentication backend uses a reserved ACCOUNT_ATTEMPT before password work and canonical Input.email for both the bucket and lookup. Unknown accounts still verify a dummy hash with the same fixed Argon2 policy. A successful locked verification stores a hashed60-second ACCOUNT_AUTHENTICATION proof bound to browser, request and credential_version. The session exchange locks account, proof and previous session, rechecks each bound fact, consumes once, rotates cookie/CSRF and preserves stable ownership with a12-hour absolute session. It refuses administrator-to-account downgrade. No standalone boolean grants authority.

Migration017 preserves015/016, records account credential epochs on sessions and revokes unverifiable pre-epoch ACCOUNT sessions without deleting account data. Session reads/CSRF and customer mutation adapters compare the current account version; restoring an old hash with a higher version cannot revive older authority. Expired account proofs join bounded security cleanup. A current schema is required for readiness. Password-change orchestration, profile/history and HTTP exposure remain separate slices; the stacked read-only customer query also compares the persisted account epoch, so stale authority cannot read booking or payment projections.
