# Administrator booking read model

P22's bounded read prerequisite exposes application/adapter ports only. Administrator HTTP, creation/change/configuration APIs and their workflow UI remain separate work; this document does not claim those routes exist.

`AdministratorBookingView.agenda` accepts inclusive Europe/Brussels civil dates, at most31 dates, and pages of1–100 entries. Midnight conversion follows Brussels DST, so one civil day can span23 or25 elapsed hours. The adapter uses a half-open instant range and orders by start instant then booking UUID. Its optional cursor advances strictly past that pair; the next cursor exists only when another row was observed. Each page is a fresh consistent snapshot, so concurrent insertions or rescheduling can change later pages. All booking states remain visible; expired pending holds are not mutated by a read.

Agenda rows contain only booking ID/reference/version/state, start, actual session end and immutable service name. They omit intake, contact data, customer identifiers, meeting links and payment references. Owner detail returns the original booking snapshot, current delivery contact/meeting/state and independent payment/refund facts for explicit private HTTP mapping later. Approval remains independent of payment.

Both reads independently validate the persisted session UUID/browser binding, ADMIN kind, enabled/enrolled administrator, matching security epoch, issued/authenticated timestamps, nonfuture last_seen_at, fifteen-minute idle deadline, eight-hour absolute deadline and revocation. Missing/invalid administrator authority fails before booking lookup; unknown booking IDs return no detail only after authorization. Ordinary reads use the live MFA session; no approved rule explicitly adds a detail-only ten-minute step-up. Existing sensitive mutation commands keep their established fresh-authentication requirement.

Each call starts an independent PostgreSQL read-only REPEATABLE READ transaction, captures database time once, and reads authority and data in that snapshot. A revocation committed before the snapshot denies access; an in-flight read can finish consistently with its earlier authorized snapshot. The query never locks scheduling/authority rows, touches sessions, expires holds or writes audit/outbox/receipts. No transport runs in its transaction. Provider errors expose only the safe STORAGE_FAILURE kind, and all new private projection containers redact toString.


## Private read HTTP slice

`GET /api/v1/admin/bookings` accepts exactly one from and through (inclusive Brussels YYYY-MM-DD), optional canonical limit1–100 (default50), and an optional opaque cursor copied from nextCursor. Unknown/duplicate/empty/noncanonical/out-of-window values fail safely. The cursor is canonical URL-safe Base64 of start/id, bounded to200 characters, and is never an authorization capability. `GET /api/v1/admin/bookings/{bookingId}` accepts no query fields and explicitly maps the private snapshot/intake and independent receipt/refund projection. Neither read bootstraps, rotates, touches or extends a session.

Both require a live persisted administrator session and independently recheck authority inside the data snapshot. Missing/revoked sessions return SESSION_REQUIRED401; other live session roles return ADMIN_ACCESS_REQUIRED403; only an authorized unknown booking returns BOOKING_NOT_FOUND404. Malformed input is INVALID_REQUEST400, and storage failure is safe retryable TEMPORARILY_UNAVAILABLE503. All bodies are no-store. Detail ETag is the numeric booking command version. Conditional cache validators are ignored and the complete current private body is returned, because independent financial facts can change without advancing that command version. Explicit servlet output prevents Spring MVC from replacing it with304. No administrator mutation route is added in this slice.

The composed runtime case reserves Order15; root expiry reserves Order14. Until that predecessor is integrated this branch has14 actual runtime cases (Orders1–13 and15); integration must preserve all15 cases and raise the minimum15. The HTTP/client contract includes explicit private DTOs, not generic serialization of domain records. New generated model exclusions are individually listed under the established generator-provenance policy.
