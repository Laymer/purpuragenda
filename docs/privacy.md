# Administrator privacy workflow

Controlled exports are available from Customers → View bookings → Customer data export. Enter a reason, prepare a private preview, review the complete customer-related notes and other content for third-party information, and explicitly confirm release. A separate action fetches the released JSON download. Do not confirm a snapshot that contains information which should not be disclosed. Exporting does not change booking ownership, immutable service/intake/policy snapshots, payment facts or notification delivery.

Every preparation, preview, release, download and idempotent replay checks current persisted administrator authority and MFA freshness (strictly less than ten minutes). Expired, revoked, disabled or changed-epoch authority cannot retrieve a previously prepared snapshot. The identifier is not a bearer token. Preparation needs a normalized10–500-character reason; unsafe HTTP requests need the existing exact Origin, session CSRF and idempotency protections. Release acknowledges third-party review and binds the exact preview digest. A retry preserves the original body/key; release never extends expiry. HTTP responses are no-store, including conditional GET requests. Downloads use a fixed attachment name and octet-stream content type containing UTF-8 JSON.

The export projects stable customer identity, optional account enrollment/profile, booking times/state/contact, immutable snapshots, private notes, amendments, contact history, override reasons, immutable receipts/refunds and refund obligations, and booking audit reasons/times. It excludes credential/session/proof/grant/token/rate-bucket/idempotency rows and notification envelopes. PostgreSQL constructs the projection in one statement snapshot, so independent account-profile writers cannot mix versions inside the export. Preparation and release use the scheduling resource lock, a single captured authoritative time and the normal transaction/expiry/idempotency machinery. Exports above16MiB of Java characters fail rather than silently truncating data.

Temporary snapshots use the existing protected delivery encryption key with a distinct CUSTOMER_EXPORT_V1 authenticated payload purpose. Each encrypted chunk binds the export/customer/administrator UUIDs, index, total count, full document digest and creation/expiry times; reordering, swapping, shortening or metadata tampering fails closed. Encryption buffers have the existing Secrets primitive limits; Java String memory cannot be reliably erased. No plaintext export is written to application files, general outbox JSON or logs. Migration019 adds metadata to the existing temporary-export table; legacy rows without authority metadata are unreadable and eligible for cleanup.

Availability is [createdAt,createdAt+1hour), using elapsed time across DST. Expiry equality rejects preview, release, download and replay. The existing hourly maintenance lane removes up to500 expired/legacy encrypted snapshots without decrypting them; failed sweeps retry on the next invocation. Ciphertext may therefore remain until the next successful sweep even though access has expired. Restore mode does not start workers and must purge temporary exports during the isolated restore procedure before access is released. Preparing a new export does not extend any older snapshot. Correction/erasure workflows must invalidate affected temporary exports before committing their change.

Preparation/review/download append durable audit events linked by export and customer UUIDs. The preparation reason remains in the privacy request and audit, but snapshots never enter audit. UI drafts/previews and Blob URLs remain in memory, clear on route/session changes and expiry, and cannot be repopulated by late responses. The downloaded file is an explicit operator-controlled copy and cannot be remotely recalled by application cleanup.

The review-deadline policy in implementation-plan.md does not execute deletion. Audited corrections are implemented as described below; reviewed erasure and tombstone replay are implemented below, with current verification limits in STATUS.md and docs/status.md. The proposed financial ten-year rule still requires accounting confirmation before public use.

## Reviewed corrections

From Customers → View bookings, choose Correct profile, Correct intake or Correct private notes. Profile correction edits the existing optional profile; a guest without a profile has no profile record to correct. Select the exact note when correcting notes. Edit the typed fields, supply a10–500-character reason without personal details, prepare the preview, review every before/after value and explicitly confirm. Fresh MFA is required for targets, preparation, preview, confirmation and retries. Reauthentication preserves only validated correction kind and booking UUID selectors, never draft values or reasons.

Migration020 stores proposals encrypted with the protected delivery key and a distinct CUSTOMER_CORRECTION_V1 purpose. The authenticated payload binds customer, administrator, target kind/UUID, baseline version/hash, proposal/reason and exact one-hour creation/expiry. Confirmation requires the original preview version1, digest and explicit true. A concurrent profile edit or correction makes the preview stale; prepare another preview. Every command uses the scheduling resource lock, one captured time and normal transaction/idempotency handling. Profile writes additionally follow the existing account-before-profile lock order. No notifications are produced by corrections.

Confirmation replaces current profile or note text, appends a durable reasoned audit without old/new plaintext, and immediately clears the encrypted proposal. Intake correction appends a typed immutable-history amendment; it does not alter original service/intake/policy snapshots. Administrator detail and exports expose effectiveIntake from the highest durable correction revision, with originals explicitly historical. Customer search matches reviewed intake names as well as retained historical names. Financial facts, booking identity, verified delivery contacts and ownership remain untouched; contact changes continue through the verified-contact workflow.

All temporary exports for the corrected customer are deleted in the same transaction, including released snapshots; unrelated customer exports remain. Saved files outside the application cannot be recalled. Durable correction facts retain target/revision and fingerprints so old legitimate note-addition and correction retries remain valid without retaining old note plaintext. Unconfirmed encrypted proposals expire after exactly one hour and the hourly maintenance lane removes at most500 expired proposals per sweep. Confirmed metadata/facts remain for reviewed retention, with no encrypted proposal. Expired or completed proposals cannot be previewed. UI values, previews and pending requests are memory-only and clear on expiry, session/route changes or destruction. Erasure must additionally cover correction proposals, reasons, amendments and durable linkage; recovery must purge pending previews before restored access.

## Reviewed erasure and restore journal

From Customers → View bookings → Review retention and erasure, select exact records, supply a reason without personal details, prepare the encrypted one-hour preview and review both selected and retained records before explicit confirmation. Record-specific holds prevent selecting held records; creating/releasing a hold requires a reason and explicit review. Twelve-month intake/note and24-month identity/history/ordinary-audit dates prompt review only. Financial records remain available for review and cannot be selected for erasure. Accounting confirmation of financial retention remains a public-use prerequisite. Erased intake is shown explicitly; immutable service/policy facts and independent receipt/refund amounts and relationships remain. Temporary exports are invalidated atomically; downloaded copies outside the application cannot be recalled.

The journal directory is required as `APP_PRIVACY_JOURNAL_DIRECTORY` (Spring property `app.privacy-journal-directory`). Local Compose mounts a separate persistent `privacy_journal` volume into backend and private operator containers, outside PostgreSQL database backups. Keep the current journal and protected delivery encryption key available independently of each database backup. Never replace the current journal with an older backup, delete it to fix startup, or delete data volumes. Startup rejects missing/corrupt/mismatched journal evidence before data access. The directory must support POSIX permissions, file locks, atomic same-filesystem rename and fsync. Existing encrypted records are size/capacity bounded; exhaustion fails closed and requires operator recovery rather than pruning history.

In an isolated restore, use the private operator with `APP_MODE=restore` and command `erasure-replay`. It validates the current external journal and replays approved recipes before access; maintenance and delivery remain suppressed afterward. Missing/corrupt journals fail and preserve restore barriers. A backup containing earlier active booking states retains its barrier and reports failure: no closure, approval, receipt or refund is invented. An operator must recover actual business facts from independent evidence first, while keeping access/delivery disabled. The private interactive `erasure-reconcile` command asks for the erasure request UUID, displays the journal digest and observed terminal booking UUID/state evidence, requires the exact digest and a reason, verifies that recovered states match and records acknowledgment before replay. It cannot change booking or financial facts. Preserve unresolved barriers until reconciliation succeeds. Subsequent delivery/access release remains a separate reviewed recovery operation; completing erasure clears only its own barrier and restores prior settings.

Every retry authenticates current administrator authority and checks recipe, journal, target and applied database evidence. Approval first commits its owned barrier, then fsyncs the external intent, then applies deterministic redaction in a resource-locked transaction. Ordinary API access is blocked during interruption; guarded administrator reauthentication and exact confirmation retries remain possible. Repeated completed replay does not erase later legitimate data. The active handoff records implementation/verification status; this documentation does not certify a release or authorize deployment.
