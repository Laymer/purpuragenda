# SMTP transport boundary

P14 transport implements a framework-free MailDelivery port and an Angus Mail adapter. It does not start a worker, render booking templates, decrypt authentication envelopes or alter the queue retry schedule (1m, 5m, 30m, 2h, 6h, 12h). Those remain separate P14/P36 work.

RESTORE suppresses direct sends before inspecting messages or accessing credentials/network. CAPTURE permits only loopback or the literal `mailpit` service; every resolved Mailpit address must be private/internal, and the checked address is pinned for that connection. Future Compose configuration must isolate Mailpit on its internal network. Arbitrary external capture destinations are rejected.

OPERATIONAL requires explicit STARTTLS or implicit TLS, normal certificate trust and hostname verification, TLS 1.2/1.3 and finite connection/read/write timeouts. Credentials come from a fresh char-array supplier and are wiped after each attempt. Jakarta Mail requires a temporary immutable password String; JVM String erasure cannot be guaranteed. No credential is stored in session properties. Debug and provider protocol logging are disabled. Message and adapter string representations redact private content/configuration; failures expose only bounded typed/numeric result classification. Stable Message-ID derives from the durable job UUID. A FAILED transport result does not authorize a worker to bypass the durable retry policy.

The test SMTP server binds loopback only. Eight mandatory tests exercise actual trusted STARTTLS and SMTPS delivery, untrusted and mismatched certificates refusing before AUTH, missing STARTTLS, UTF-8 and dot transparency, stable Message-ID, 451/550 replies, connection failures, capture address restrictions, password erasure and restore suppression. Certificates and private keys exist only in memory; assertions never render credentials or message content. No live provider or email account is contacted. The exact-class report guard rejects missing, truncated, unrelated, failed or skipped suites. Provider launch acceptance remains a later operational decision.

Dependencies use Spring Boot 4.1.2 BOM-managed Jakarta Mail API 2.1.5 and Angus Mail 2.0.5. Test certificate generation pins Bouncy Castle bcpkix/bcutil 1.86, aligned with existing bcprov 1.86. Provenance: official Maven Central coordinates `org.bouncycastle:bcpkix-jdk18on:1.86` (publisher/license/SCM and bcutil dependency verified against its published POM); production TLS settings follow the official Angus SMTP provider documentation.

Sources: https://repo.maven.apache.org/maven2/org/bouncycastle/bcpkix-jdk18on/1.86/bcpkix-jdk18on-1.86.pom and https://eclipse-ee4j.github.io/angus-mail/docs/api/org.eclipse.angus.mail/org/eclipse/angus/mail/smtp/package-summary.html

P14 authentication-delivery foundation stores each 15-minute challenge and its encrypted AUTH job in one READ COMMITTED transaction using one captured database time. CREATE/ACCOUNT require a browser hash and no booking; MANAGE/CONTACT require a booking and no browser hash. These bindings do not prove the caller's authority: P15/P33 must enforce verified authority and challenge redemption. Receipts return IDs/expiry only, never the token. The versioned binary envelope exists only as authenticated ciphertext in the job; token hashes alone are stored on challenges.

Preparation locks the job and challenge and reads suppression before capturing authoritative time. It verifies the current lease token, strict lease/challenge expiry, unconsumed challenge and every envelope identity/purpose/scope/browser/hash field. Invalid, expired or suppressed jobs lose ciphertext and their lease atomically. Existing fenced queue completion clears ciphertext after delivery. This slice does not start a worker or an expiry sweeper; the following worker slice must erase expired queued work as well as prepare due work.

The delivery Secrets instance is explicitly separate from the TOTP key by composition; enforcing that actual operational wiring remains a P45 gate. No wiring enforcement is claimed here. Preparation is a point-in-time check: challenge consumption/revocation during SMTP can still produce an email containing an inert link. Redemption must independently recheck single use, expiry, purpose and browser scope. SMTP is outside this store's transaction; stable Message-ID and fenced callbacks do not promise exactly-once network delivery.
