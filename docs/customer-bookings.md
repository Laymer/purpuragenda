# Customer booking HTTP

This document describes the P20 implementation slice. Its draft is stacked on the authorized-query PR69; merged status and exact verification are recorded in STATUS.md and the PR. The OpenAPI contract and regenerated Angular client describe all four operations; typed protocol tests exercise their headers, receipts and safe failures.

The routes are /api/v1/bookings (POST), /api/v1/bookings/{bookingId} (GET), and the /cancel and /reschedule POST suffixes. A public reference is never authority. A live customer session must derive from an actual email proof or account authentication. Guest access is restricted to one booking; account ownership follows the stable customer identity.

All writes pass the existing exact-Origin, persisted-session and CSRF guard and then recheck authority inside the resource-locked scheduling transaction, before receipt lookup. Creation requires Idempotency-Key; both changes additionally require a single strong If-Match such as the version returned by the booking response. Missing versions return428, stale versions412, business conflicts409. Unknown and unowned targets are404; an invalid or revoked session returns401 uniformly before looking up any target. Creation without usable authority returns403.

JSON bodies are limited to16KiB, with exact root and intake field sets, duplicate/trailing-data rejection and no string-to-number coercion. Civil birth time is HH:mm or HH:mm:ss without zone inference. Start time is an explicit offset datetime at microsecond precision;24:00 and leap-second normalization are rejected. Unexpected storage/provider failures return a constant503 problem without exception details.

Creation accepts serviceId, serviceVersion, policyVersion, startInstant, displayZone, noticeVersion and intake. Intake contains firstName, lastName, telephone, birthDate, birthTime, birthplace and message (which may be empty). Cancellation takes an empty JSON object. Rescheduling takes policyVersion and startInstant; the original snapshot and pending-expiry ceiling remain unchanged. The local notice version defaults to local-v1; operational mode requires an explicit non-local configured version. Public reviewed booking terms/notice delivery to the future intake UI remains a separate required integration; these local fixtures are not legal approval.

Successful commands return bookingId/version, a strong version ETag and Cache-Control:no-store. Creation returns201 plus Location; changes return200. Repeating a key with the same normalized request returns the committed receipt; changing its content returns IDEMPOTENCY_KEY_REUSED. After an uncertain response, retain the same key and body, then GET the current authorized booking rather than interpreting a replayed receipt as current state.

GET uses safe session inspection and one enforced read-only database snapshot for current authority, booking and independent payment facts. It never touches idle lifetime, locks scheduling rows or reclaims expiry. The response includes service snapshot, current delivery contact, session times/display zone, deadlines, allowed actions and monetary summaries. It excludes intake, stable-customer/account identifiers and external payment references. pendingExpired explicitly marks a due hold awaiting reclamation while stored state/version remain unchanged. Meeting URLs are exposed only for confirmed bookings. All responses are noncacheable; payment changes are not inferred from booking confirmation. GET ignores conditional cache validators and returns the current authorized representation with200: independent payments and elapsed deadlines can change without a booking-version change. The strong version ETag is the command precondition, not evidence that the entire read representation is unchanged.

Tests use real proof issue/redemption, PostgreSQL and application commands. The20-way MockMvc creation race is component evidence, not the separate two-backend process/load acceptance gate. Actual network HTTP/runtime composition and real SMTP durability have separate tests; no production authentication bypass is introduced.

## Guest management target

`GET /api/v1/guest/booking` derives exactly one booking from the persisted guest grant in the browser session. It accepts no target/query parameters and never chooses from account history. A consumed creation grant can resolve its bound management target; an unused creation grant cannot. Direct management and derived management scopes retain all existing ownership, browser, lifetime, revocation and parent-grant checks. Resolution, authority, booking and independent money share one enforced read-only REPEATABLE READ snapshot and database time, without session activity touches or resource locks.

The response is the existing private customer status shape, explicit200/no-store and command-version ETag even with conditional headers. Missing/expired browser authority returns401; a valid session without a scoped guest booking returns404. Account history uses its separate account workflow. Unsupported parameters return400 and storage errors remain safe503 problems. No intake or account identity is projected.

Protected `GET /api/v1/bookings/{bookingId}/availability` accepts exactly `from`, `to` and `displayZone` (up to 31 inclusive dates). It uses the same read-only repeatable-read authority snapshot for booked terms, current policy/calendar, occupancy and active allowance. It excludes the booking itself, retains its original duration and pending expiry buffer even after service archival, and never charges submission quota or touches the session. Confirmed bookings do not acquire a pending buffer. A passed original change cutoff or expired hold returns no slots with `BOOKING_NOT_CHANGEABLE`; absent scope returns the same private 404 as an unknown booking. Responses are no-store and advisory; the versioned rescheduling command still rechecks every rule under the resource lock.

Both public and protected availability consume the same persisted120-per-minute client-network bucket before parsing or reading, including malformed booking IDs and normalized path variants. The advisory snapshot itself stays read-only; the separate admission filter fails closed if its storage is unavailable.
