# Scheduling domain contracts

Europe/Brussels defines business dates, weekly windows, date exceptions and the midnight-anchored start grid (1–120 minutes). Windows permit starts in [start,end); the actual session and 120-minute reservation may cross ordinary closing times or breaks. Default daily windows offer 09:00 through 19:30 on a 30-minute grid. Adjacent or intersecting windows merge; inherited windows apply unless replaced/closed by an exception. ADD windows merge with inheritance.

Nonexistent DST local times yield no candidates. Repeated times yield both distinct instants, in instant order. Display-zone selection and offset labels belong to later application/UI tasks. Minimum notice is elapsed time, inclusive at equality. The inclusive horizon adds one calendar month in Brussels, clamps month ends, advances through gaps and retains the source offset when valid during an overlap. Captured authoritative time must be supplied by the application transaction.

Pending expiry is the earlier of creation plus lifetime and start minus buffer, and must be strictly after creation. Customer cutoff comparison is inclusive. Daily, active and request limits remain separate rules; capacity zero blocks new requests. The application must obtain accurate counts and preserve immutable submission charges under its resource lock.

A hard blackout intersects the full reservation, including time after the session ends. An administrator override requires a reason and explicit rules, including every intersecting blackout ID. Existing reservation overlap and nonfuture starts cannot be overridden. Domain rule evaluation never performs persistence or authorizes an actor; later application and PostgreSQL tasks enforce these decisions atomically.

`SchedulingCommands` composes the internal mutation boundary: the unit acquires its resource lock and captures PostgreSQL time, checks idempotency, reclaims due holds, then opens the attempted mutation's savepoint. Explicit scheduling/state business failures become closed-code receipts. They roll back the attempted booking and its quota charge while retaining earlier expiry, refund obligations, audit and outbox effects. Unknown failures, invalid persisted data and failures during reclamation abort the entire command. The PostgreSQL overlap constraint still returns `SLOT_UNAVAILABLE` through the same savepoint.

Receipts retain the original `{code,entityId,version}` format; failure codes are additive and carry neither arbitrary messages nor personal data. Identical replay returns the stored receipt without rerunning the mutation, while changed fingerprints return `IDEMPOTENCY_KEY_REUSED`. This runner does not establish authority or expose an HTTP endpoint; authorized creation must still resolve its persisted grant inside the same locked transaction.

`CustomerBooking` validates customer creation through a typed transaction port. It accepts a session reference, reviewed service/policy/notice versions, a start, intake and display zone. It obtains the stable customer identity and verified email from the transaction. All normalized request fields contribute to the idempotency fingerprint. Current service/policy values become immutable snapshots; daily, active and submission limits remain independent. The full reservation, including the next business date for late starts, must be free. Saving, charging, binding the creation grant and recording effects belong to one attempted mutation.

`CustomerBookingUnitOfWork` is an unwired application port at this checkpoint. Its future PostgreSQL adapter must lock and recheck the current session/grant before receipt lookup, derive the actor scope, and atomically commit or roll back those effects. Application unit tests do not establish that persistence or authorization guarantee. No public creation endpoint is enabled by this slice.

Anonymous availability now loads two extra elapsed hours after the last whole Brussels date, so a next-date booking cannot be hidden from a late start's reservation check. This expands the occupancy scan, not the requested display dates or daily-capacity definition.

## Administrator creation

`AdminBooking` is the internal administrator creation command; its PostgreSQL `AdminBookingUnitOfWork` adapter (`PostgresAdminBooking`) is implemented and HTTP exposure belongs to P22. The request carries no actor and no administrator flag. The adapter takes the shared resource lock, locks the administrator, then the session, and rechecks after the lock, at the captured database time and before any stored receipt: kind ADMIN, not revoked, issued, inside the 8 hour absolute and 15 minute idle limits, administrator enabled and enrolled, session security epoch equal to the administrator epoch, and multi-factor authentication within the last 10 minutes (equality is expired). Guest, account and anonymous sessions are `FORBIDDEN`; every other failure is `AUTHENTICATION_REQUIRED`. The idempotency scope is the administrator id with operation `ADMIN_CREATE_BOOKING`.

The command checks reviewed service, policy, calendar and notice versions (stale values are expected failure receipts, `CALENDAR_CHANGED` is additive), finds or creates the stable customer identity for the supplied email in the same transaction, and validates the full 120 minute reservation. Administrator creation consumes daily capacity and the customer's active allowance but is never charged to, nor limited by, the customer submission quota. An override names explicit rules plus a reason of 10 to 500 characters; hard blackouts additionally require every intersecting blackout id. Overlap with an unreleased reservation and nonfuture starts are never overridable; the PostgreSQL exclusion constraint independently protects overlap. A participant URL creates a confirmed booking (manual basis); otherwise a normal pending hold is created, and an impossible short-notice hold fails.

Success writes the booking, snapshot and occupancy, an `ADMIN_CREATED` audit event (with reason and rule names) and outbox event, and, when an override was used, an immutable `booking_override` row. A successful receipt that lacks exactly those effects fails the transaction. Expected failure receipts keep earlier expiry reclamation and roll back the attempted booking and any newly created identity; unexpected failures roll back everything.

Overrides must be used: naming a rule that is not violated, or a blackout that does not intersect the reservation, fails with the additive `OVERRIDE_UNUSED` receipt so audit and `booking_override` rows record only what was needed. A participant meeting id already held by any booking fails with the stable `MEETING_IN_USE` receipt, checked under the resource lock before saving (the database unique constraint remains the last defence).

Identity risk: the administrator supplies the customer email and the stable identity is found or created from it. A mistyped but valid email attaches the booking to a third party's identity (and its active allowance and history). The identity row records only administrator attestation; it grants no access, because guest access still requires proof of that mailbox. The administrator interface (P22/P28) must show the normalized email for confirmation, and corrections are audited contact changes, not silent edits.
