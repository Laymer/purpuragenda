# Durable customer reminders

Confirmed bookings receive customer reminders at 48 elapsed hours and 2 elapsed hours before the actual session start. Grace windows are 60 minutes and 15 minutes. Deadlines use Instant arithmetic across Brussels DST/month boundaries. Pending/terminal bookings create no reminders.

Eligibility belongs to the persisted confirmation/reschedule outbox event time: a deadline strictly before that event is skipped; equality remains eligible. An expander delayed until after an eligible deadline still creates its original job. Dispatch requires the half-open interval `[scheduled_at, scheduled_at + grace_seconds)` and a future confirmed session, so grace equality is expired and delayed/retried work never extends the window. Immediate notifications still use the expansion transaction's one captured database time.

Migration 014 is appended after applied 015/016/017. It adds original `scheduled_at`, validates reminder audience/event/booking/grace metadata and protects the reminder's original identity/window with an update trigger. Retry `due_at` may change; original schedule/grace/event/version may not. Existing immediate jobs remain unchanged. Historical reminder-shaped rows without valid metadata make upgrade fail closed rather than invent a deadline or replay mail. Readiness requires the new columns and validated constraint. The same trigger also forbids changing `booking_id` on a reminder row, so P35 erasure/anonymization must delete, suppress or tombstone reminder rows rather than re-point or null their booking reference.

Expansion reads current booking state/start without taking a booking row lock while holding its outbox row, avoiding scheduling lock inversion. Delivery rereads current recipient, service snapshot, session time and meeting link. Later rescheduling, cancellation or confirmation suppresses earlier reminder revisions; a delayed pending ADMIN_CREATED event cannot duplicate its later approval reminder. Independent payment/refund facts do not suppress a valid reminder. A confirmed booking without a meeting link at delivery time permanently suppresses that reminder as MEETING_UNAVAILABLE; adding a link later does not revive it. No intake, private notes, birth fields or authentication tokens enter reminder content.

SMTP remains outside database transactions with fenced leases, operator suppression, bounded retries and stable Message-ID. Crash-after-acceptance duplicates remain possible. Relevance is checked when the job is loaded, before the SMTP send, so a cancellation or reschedule that commits during that window can still let one stale reminder go out, the same residual window as other notifications. Restore mode and runtime worker composition remain coordinator-owned P45/P47 work; this slice neither starts background lanes nor releases historical mail after restore. Meeting-change/contact-change notification workflows and calendar attachments remain separate slices.
