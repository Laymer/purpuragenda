7. NEXT SECURITY/HTTP DESIGN (AGREED, NOT IMPLEMENTED)

P17 should be split into session/origin/CSRF foundation, persisted throttles and
bounded cleanup, then protected authentication endpoints. Do not expose login
or email issuance before distributed limits and CSRF/origin checks are effective.

- Persisted CSRF is digest-only, so reload needs a safe reissue path. Proposed
  exact-origin POST /session/bootstrap creates anonymous authority or rotates
  only CSRF for a current live session. GET /session returns safe role/deadlines;
  CSRF-protected POST /session/logout revokes and clears the cookie. These are
  route intentions under the versioned API, not existing implemented endpoints.
- Unsafe API requests require exact configured Origin, live persisted session
  and X-CSRF-Token; reject null/multiple origins and cross-site Fetch Metadata.
  Do not derive canonical origin from forwarded headers. Private replies are
  no-store, with safe problem codes/correlation identifiers, never raw errors.
- Operational cookie: __Host-purpuragenda, Secure, HttpOnly, SameSite=Lax, Path=/,
  no Domain. Use a distinct local HTTP cookie. Rotate after authentication and
  privilege changes with new CSRF. Keep tokens/intake in memory only.
- Normal MFA proof can stay server-internal: generate random request binding,
  run factor transaction, consume proof in the same HTTP handler. Recovery spans
  requests and needs persisted request/browser binding; reenrollment must never
  yield ordinary admin authority. Email-fragment GET stays inert, removes the
  fragment and requires explicit CSRF-protected POST redemption.
- Lock order: admin -> proof -> previous session for admin exchange; scheduling
  resource -> P15 booking/challenge locks -> previous session for guest exchange.
  Capture time at the prescribed locked boundary. Session-only touches/logout
  must never later acquire grant/admin locks. Preliminary HTTP checks cannot
  replace mutation-time persisted-authority rechecks before receipt lookup.
- rate_limit_bucket uses sorted multi-bucket locks and one DB time. Email60s
  cooldown,5/hour/address,30/hour/IP; admin5failed attempts/15m/account+IP;
  availability120/min/IP. Atomic Retry-After; use scoped HMAC identifiers, no raw
  email/IP logs/storage. Reserve concurrent admin attempts before factor work;
  successful release may decrement only the same window, not a reset window.
- Separate rate HMAC key and version: APP_SECURITY_RATE_KEY_FILE and
  APP_SECURITY_RATE_KEY_ID. Do not reuse TOTP/delivery keys. Local initializer
  supplies local-rate-v1; operational mode rejects local defaults.
- Session cleanup can commit session-only work separately. Mixed grant cleanup
  must acquire resource -> grants -> referencing sessions, delete children before
  parents, and respect challenge FKs. Delivery lock order is job -> challenge;
